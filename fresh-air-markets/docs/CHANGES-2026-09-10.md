# What changed on September 10–11, 2026

This is the plain-language record of the work that took the portal from a
draft pull request with no production database to a live site on
`freshairmarketsandevents.com` with applications, review, documents,
reservations, Square payments, and email. It also describes the architecture
as it stands now. Commit hashes are on `main`.

## 1. Where things started

- PR #1 (`codex/vendor-booking-validation`) contained the application review,
  agreement, document, reservation and Square payment build, but Production on
  Vercel had **no database**. Only `AUTH_SECRET` was set; the Neon database was
  connected to Preview only. The live site ran the in-memory demo store and
  forgot everything on each cold start.
- There was no supported way to migrate or create a manager account on a
  production database: the runner and bootstrap only accepted a Preview/QA
  target, public signup was closed, and the app seeded the public demo login
  (`demo@freshairmarkets.app` / `sunrise-demo`) into any empty database.
- Vendor applications could only enter through HighLevel webhooks. Documents
  could only enter through an external transfer worker and malware scanner
  that did not exist, so no vendor could ever reach a reservation or payment.
- Payments were hard-pinned to the marketing domain, which was a separate
  AI Studio site, so live payments could not run from Vercel at all.

## 3. Architecture now

```
Vendor browser ──► freshairmarketsandevents.com (Next.js 15 on Vercel, project farmers-market)
                     │
                     ├─ /            marketing home, newsletter, contact form
                     ├─ /vendors     benefits, requirements, fees, FAQ
                     ├─ /about
                     ├─ /apply       application + electronic Vendor Agreement signature
                     ├─ /agreement   the agreement text
                     └─ /vendor/payment   private, single-use payment page (Square hosted checkout)

Staff browser ─────► /login → /applications, /applications/{id}, /messages
                     review · documents · final reservation · Square checkout · private vendor link

PostgreSQL (Neon, production branch) ── migrations 001–024, applied by scripts/database-readiness.mjs
Square (production) ── hosted checkout links; webhook → /api/payments/square/webhook
Resend ── outbound email; every attempt logged in fame_email_log
GitHub Actions ── payment-scheduler.yml every 5 min → /api/internal/cron/* (expires unpaid 48-hour holds)
```

### Vendor journey

1. Vendor applies at `/apply`: identity, business, category, booths per market
   day (1–4), full season or specific Saturdays, and a typed signature accepting
   the Vendor Agreement. `POST /api/apply` writes the application through the
   same idempotent handoff writer the CRM path used, with portal-generated
   contact and opportunity identifiers, and records the signature as the
   agreement completion. Vendor and staff get emails.
2. Staff review at `/applications/{id}`: approve, request changes or decline.
   The vendor is emailed the decision.
3. Staff upload the vendor's certificate of insurance (and food license when
   required) on the same page and approve them.
4. Staff finalize the reservation (dates and booth count, pre-filled from the
   application). Capacity and category limits are enforced in the database.
5. Staff create the Square checkout, then the private vendor link. The vendor
   is emailed the link, total and 48-hour deadline.
6. The vendor pays through Square's hosted page. Square's webhook marks the
   reservation paid; vendor and staff get confirmation emails. Unpaid holds are
   released by the scheduler after 48 hours.

### Data

All state is in PostgreSQL. Key tables: `fame_applications` and
`fame_application_events` (immutable source snapshots), `fame_agreement_*`,
`fame_application_documents` plus `fame_private_document_objects` (bytes),
`fame_reservations` / `fame_reservation_finalizations` / allocations,
`fame_payment_orders` and `fame_square_webhook_events`, `fame_email_log`,
`fame_contact_messages`, `fame_newsletter_subscribers`. Every table is scoped
by `market_id`; the staff session is the only tenant selector.

### Configuration (Vercel Production)

`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `AUTH_SECRET`, `FAME_MARKET_ACCOUNT_ID`,
`FAME_SEASON_ID`, `FAME_BOOTH_CAPACITY`, `FAME_VENDOR_PORTAL_ORIGIN`,
`SQUARE_ENVIRONMENT=production`, `SQUARE_ALLOW_LIVE_PAYMENTS=true`,
`SQUARE_ACCESS_TOKEN`, `SQUARE_LOCATION_ID`, `SQUARE_MERCHANT_ID`,
`SQUARE_WEBHOOK_SIGNATURE_KEY`, `SQUARE_WEBHOOK_URL`, `CRON_SECRET`,
`RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_REPLY_TO`, `STAFF_NOTIFY_EMAIL`.
GitHub Actions variables: `FAME_PAYMENT_SCHEDULER_ENABLED=true`,
`FAME_VENDOR_PORTAL_ORIGIN`; secret `CRON_SECRET`.

### What is no longer used

HighLevel. Its routes, workers and variables remain in the code but every
worker reports `{ enabled: false }` without HighLevel configuration, and no
part of the vendor journey depends on it. `GHL_LOCATION_ID` is reused only as
the location label on portal applications.

## 4. Operating notes

- **Runbooks**: `docs/production-database-bringup.md` (database),
  `docs/portal-native-site.md` (site, intake, email),
  `docs/square-production-runtime.md` (payments).
- **Tests**: `npm test` (isolated) and `npm run test:pg` (real PostgreSQL) must
  both pass before a push; the GitHub CI runs them on PostgreSQL 17 and 18.
- **Emails** are best-effort with a log, not a retry queue. The review screen
  and API responses say `sent`, `failed` or `not_sent` honestly.
- **Email sender**: `hello@freshairmarketsandevents.com`, verified in Resend on
  September 11, 2026 (DKIM on `resend._domainkey`, MX and SPF TXT on `send`).
  Resend rejects reserved test domains such as `example.com`, so use a real
  mailbox when testing vendor emails.
- **Not yet built**: market-day reminder emails and the Vendor Pass. Vendors
  can upload insurance and food-license documents right after applying.
